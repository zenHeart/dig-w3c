🛡️ 浏览器沙箱与 Session 隔离

深入分析：Web 页面嵌入第三方 URL 时，如何实现类似 Electron sessionStorage 的登录态隔离效果

一、背景：为什么需要 Session 隔离？

场景描述

Web 页面内部嵌入第三方 URL，切换 Tab 时需要支持不同登录态。类似于 Electron 的 sessionStorage 隔离效果——每个 BrowserWindow 有独立的 Session。

核心问题：传统 Web 中，sessionStorage 按 origin 划分。同 origin 下的不同"身份"默认共享同一份 sessionStorage。

核心概念

Origin（源）

origin = protocol + "//" + host + ":" + port
Example: https://example.com:443

sessionStorage/localStorage/cookies 按 origin 隔离。不同 origin 之间无法互相访问存储。

Electron vs Web

二、关键隔离机制

2.1 Sandbox 属性

<iframe sandbox> 通过指令控制隔离级别：

sandbox 值效果
（无 sandbox）继承父页面全部权限
allow-same-origin将 iframe 视为同源（可访问父页面 DOM）
无 allow-same-originiframe 成为 unique origin
allow-scripts允许执行脚本
allow-forms允许表单提交

2.2 COOP（Cross-Origin-Opener-Policy）

控制窗口之间的关系，决定是否共享 Browsing Context Group：

Cross-Origin-Opener-Policy: same-origin | same-origin-allow-popups | unsafe-none
值效果sessionStorage 隔离
same-origin强制独立 BC Group✅ 完全隔离
same-origin-allow-popups允许与跨域 popup 通信⚠️ 部分隔离
unsafe-none默认，允许跨域访问❌ 共享
COOP same-origin 核心效果：即使 top-level origin 相同，设置了 COOP 的文档会进入独立 BC Group，sessionStorage 完全隔离。

2.3 COEP（Cross-Origin-Embedder-Policy）

Cross-Origin-Embedder-Policy: require-corp | credentialless

credentialless 让 iframe 以无凭证模式加载（不携带 cookies），适合隐私隔离。

2.4 Storage Partitioning（存储分区）

现代浏览器为防止追踪，对存储按 top-level origin 分区：

顶级页面: partition_key = (top-level origin, agentClusterId)
第三方 iframe: partition_key = (top-level origin, nav-site, agentClusterId)

这意味着即使 iframe 内 URL 相同，不同顶级页面下的 iframe 也有不同的存储空间。

2.5 Storage Access API

允许被嵌入的第三方 iframe 在用户交互后访问 cookies：

// 在 iframe 内调用
const granted = await document.requestStorageAccess();
if (granted) {
  // 可以访问 cookies / sessionStorage / localStorage
}
限制：需要用户交互触发，浏览器可能拒绝。

方案 A：COOP + 多 iframe 实例

步骤：

  1. 第三方应用配置 Cross-Origin-Opener-Policy: same-origin
  2. 宿主页面为每个会话创建独立 iframe
  3. 通过 postMessage / BroadcastChannel 通信
<!-- 宿主页面 -->
<script>
function createSession(sessionId) {
  const iframe = document.createElement('iframe');
  iframe.sandbox = 'allow-scripts allow-forms allow-popups';
  iframe.src = `https://third-party.com/app?session=${sessionId}`;
  iframe.style.display = 'none';
  document.body.appendChild(iframe);
  return iframe;
}
</script>

方案 B：动态子域名

为每个登录态分配独立子域名，实现完全 origin 隔离：

session-a.third-party.com  → 登录态甲
session-b.third-party.com  → 登录态乙
session-c.third-party.com  → 登录态丙
优点：完全同标准浏览器行为隔离，无需特殊 Header
缺点：需要服务端配置多子域名

方案 C：Electron 类比方案

模拟 Electron 的多窗口多 Session 模型：

// 每个"登录态" = 一个独立 window
const sessions = {
  'user-A': window.open('https://third-party.com', 'winA'),
  'user-B': window.open('https://third-party.com', 'winB'),
};

// 切换时隐藏/显示对应窗口
function switchSession(sessionId) {
  Object.entries(sessions).forEach(([id, win]) => {
    if (id === sessionId) {
      win.focus();
    }
  });
}
注意：sessionStorage 仍按 origin 共享，与 Electron 不同。
